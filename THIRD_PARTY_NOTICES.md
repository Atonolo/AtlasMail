# Third-party and license status

The project is MPL-2.0. The direct development dependencies currently selected
in `package.json` are Electron 45.2.1 and electron-builder 26.18.0, both
declared MIT by their npm packages. Node.js is distributed under its own
license and includes third-party components. Electron additionally bundles
Chromium, Node.js and other components with separate license notices.

`npm run license:check` enumerates **installed npm package manifests**,
including nested development dependencies, and blocks unknown, malformed or
non-allowlisted SPDX expressions. The versioned npm lockfile pins their
resolution. The check accepts a dual-license expression only when an approved
choice exists and every alternative is known. In particular, it selects ISC
for `sanitize-filename` and `is-integer` and MIT for `type-fest`; their
alternative WTFPL or CC0-1.0 terms are not OSI-approved. Python-2.0 is
OSI-approved. The original WTFPL-only `truncate-utf8-bytes` build dependency
is overridden with the MIT-licensed `unicode-byte-truncate` 1.0.0; a contract
test covers the filename sanitizer's UTF-8 byte limit and reserved names.

**Release blockers:** Electron 45.2.1's bundled `LICENSES.chromium.html`
lists the Ooura 2-dimensional FFT package under the
[Ooura 2001 license](https://scancode-licensedb.aboutcode.org/ooura-2001.html),
which is not OSI-approved. It also lists libjpeg-turbo's libjpeg API under
the [IJG license](https://spdx.org/licenses/IJG.html), which
[SPDX records as not OSI-approved](https://raw.githubusercontent.com/spdx/license-list-data/main/json/details/IJG.json).
The libjpeg-turbo BSD license applies to different code; it is not an
alternative license for the IJG-derived libjpeg API. SQLite is
[public domain](https://sqlite.org/copyright.html), not distributed under an
OSI-approved license; its notice is identified in SPDX as
[`blessing`](https://spdx.org/licenses/blessing.html). This is a conflict
with the issue's explicit OSI-only dependency requirement, not a claim that
SQLite's public-domain code is generally unlawful to use. The gate explicitly
rejects all three notices, even if a binary-audit record is added. It also
rejects the Node.js runtime running the check when `process.versions.sqlite`
identifies Node's bundled SQLite, independently of Chromium's notices.
Electron's
[build rule](https://github.com/electron/electron/blob/v45.2.1/BUILD.gn)
copies Chromium's `about_credits.html`, which is generated by a
[source-tree scan](https://github.com/chromium/chromium/blob/156.0.8078.75/components/resources/BUILD.gn)
without specifying an Electron GN target. Consequently, a notice alone
does **not** prove that its code is linked into Electron. However, official
Electron 45.2.1 debug symbols for all four target binaries map the FFT
functions `cdft`, `rdft` and `rdft2d` to `third_party/fft2d/src/fftsg.c`
and `fftsg2d.c`. They also map `chromium_jpeg_CreateDecompress`,
`chromium_jpeg_read_header` and `chromium_jpeg_read_scanlines` to
`third_party/libjpeg_turbo/src/jdapimin.c` and `jdapistd.c`. The
[pinned JPEG source](https://chromium.googlesource.com/chromium/deps/libjpeg_turbo/+/640f254ad0fa03f6b1f29f89b7dd9366f2f6e533/src/jdapimin.c)
identifies that code as IJG-derived. The symbols also map
`chrome_sqlite3_step` to Chromium's `third_party/sqlite/src/amalgamation/sqlite3.c`
and `sqlite3_step` to Electron's bundled Node
`third_party/electron_node/deps/sqlite/sqlite3.c`. The symbol module IDs were
matched to the PE CodeView, ELF build ID or Mach-O UUID in the corresponding
executable or framework:

With Python 3, `python scripts/inspect-electron-symbols.py <symbol-zip>
--expected-id <module-id> --component fft` reproduces the FFT
function-to-source check after verifying the downloaded ZIP's SHA-256; use
`--component jpeg` for JPEG and `--component sqlite` for SQLite. The
inspector's synthetic positive and negative tests can be run with
`python -m unittest discover -s test -p test_inspect_electron_symbols.py`.
The Windows `electron.exe` SHA-256 was
`32e357fc856feadd1e51531f47811d2621483e5a58815eb4999154d7c9baea3b`;
the Linux and macOS binaries were inspected directly inside the official
platform ZIPs. These are binary-inspection results, not application execution
or installation tests on Linux or macOS.

Chromium's
[FFT metadata](https://github.com/chromium/chromium/blob/156.0.8078.75/third_party/fft2d/README.chromium)
marks it as shipped, and
[its WebRTC target](https://github.com/chromium/chromium/blob/156.0.8078.75/media/webrtc/BUILD.gn)
unconditionally depends on TensorFlow Lite. The latter's
[kernel targets](https://github.com/chromium/chromium/blob/156.0.8078.75/third_party/tflite/BUILD.gn)
depend on FFT2D. Removing a notice or merely disabling WebNN would therefore
not demonstrate a compliant build. The non-OSI components must be replaced
or removed, and each resulting binary and its complete dependency audit
must be verified before release.

An alternative prebuilt runtime was investigated, not adopted: Flutter
3.47.9's official Windows x64 release engine
([ZIP](https://storage.googleapis.com/flutter_infra_release/flutter/89c39edfdfae2949f6806e4a315c0c08522238b7/windows-x64-release/windows-x64-flutter.zip),
SHA-256 `37c20db268f4c99808e9a95b03d0f10246f6cb81b7aa6497e978ac443175210a`)
also links IJG-derived libjpeg-turbo code. Windows Debug Help loaded its
`flutter_windows.dll.pdb` with `PdbUnmatched = false` and source lines
available. Its PDB GUID was `700a6c47-4678-4832-b977-375a7747070c`, age 1;
the DLL and PDB SHA-256 values were respectively
`30494fb08f9f101a8fbe42568110aaa160efbd7341f3cfe877dc14214be3a233` and
`af44935fe4d23674c00b2a84adcc18e5b9b6ebf4a13a6f29f63eee373337ce6a`.
`jpeg_CreateDecompress` and `jpeg_read_header` mapped to `jdapimin.c`, and
`jpeg_read_scanlines` to `jdapistd.c`, under Flutter's
`third_party/libjpeg-turbo/src`. Its
[pinned source](https://flutter.googlesource.com/third_party/libjpeg-turbo/+/0fb821f3b2e570b2783a94ccd9a2fb1f4916ae9f/jdapimin.c)
identifies the same IJG terms. Flutter therefore cannot be assumed compliant
merely from its BSD framework license. This is not a full Flutter audit or
evidence for its other platforms.

Another unadopted candidate, wxWidgets 3.2.12, was built as an isolated
Windows x64 sample from its
[official source ZIP](https://github.com/wxWidgets/wxWidgets/releases/download/v3.2.12/wxWidgets-3.2.12.zip)
(SHA-256 `1f7ec935dddbba5cf454795dc255ef1e21c668533f5a5951a6034f2949c80433`).
The sample was configured with its JPEG, PNG, TIFF, SVG, Tango art, regex,
zlib, expat and webview features disabled, and its minimal window started
locally. Its executable SHA-256 was
`e00936ee084776fb4b2bef3c21914b281eb7e02d2f1cdf2eda89f5ac66d2a9a1`.
It was built using Microsoft Visual C++ 19.44 and imports Microsoft C++
runtime DLLs. These facts are only a Windows feasibility probe, **not** an
OSI-compliant toolchain or binary audit, an accessibility assessment, or
evidence for macOS/Linux. A replacement runtime, native UI and web/core
integration would all still need validation. Node's upstream notices also
describe public-domain time-zone data used by ICU; its actual presence and
the complete dependency graph require review for any proposed Node build.

Two additional feasibility checks do not establish compliant replacements.
Node 26.13.0's [configure script](https://github.com/nodejs/node/blob/v26.13.0/configure.py)
supports `--without-sqlite` and `--without-intl`; no such cross-platform build
or binary audit has been completed, and the Windows `vcbuild.bat` interface
does not expose a SQLite-disabling option. Separately, an isolated Go 1.27.3
and Gio 0.10.3 Windows x64 sample displayed a synthetic button. Its executable
SHA-256 was
`395f3bcc56af85c9e7f7e419252ecd1dcd6200529f5d02e3f1c6655708cf461f`.
Windows UI Automation reported no descendants under that sample's window.
A native Windows Forms control used as a baseline exposed its name but was
reported as a pane without action patterns, so this observation is not a
conclusive screen-reader or accessibility assessment. Neither the sample
nor Gio has undergone a complete cross-platform dependency and license
audit.

Electron 45.2.1's upstream
[build arguments](https://github.com/electron/electron/blob/v45.2.1/build/args/all.gn)
also enable `proprietary_codecs` and set `ffmpeg_branding` to `Chrome`. These
settings warrant a separate codec/patent and redistribution review; their
names alone do not establish that the source code uses a non-OSI license.

## Firefox test runtime

The source issue applies its OSI requirement to test dependencies as well as
runtime and build dependencies. The Firefox smoke test is therefore not
exempt. Official Mozilla Breakpad symbols matched to the CodeView IDs of
the Windows Firefox ESR 153.6.0 and Firefox 159.0.1 test binaries map
`jpeg_CreateDecompress` and `jpeg_read_header` in `xul.dll` to
`media/libjpeg/src/jdapimin.c`. The corresponding
[ESR source](https://github.com/mozilla-firefox/firefox/blob/a34c4160e3f75ab9918fbe4669ff7ae56f1977c8/media/libjpeg/src/jdapimin.c)
and [159 source](https://github.com/mozilla-firefox/firefox/blob/6181e6b5f28a8fbae1d5c3ef6f6626b5a2180213/media/libjpeg/src/jdapimin.c)
identify the IJG-derived code, and their
[libjpeg-turbo license](https://github.com/mozilla-firefox/firefox/blob/a34c4160e3f75ab9918fbe4669ff7ae56f1977c8/media/libjpeg/LICENSE.md)
applies IJG terms to the libjpeg API.

The `xul.dll` SQLite public symbols are import thunks to `nss3.dll`, not
source-line evidence on their own. The matching NSS symbols map the exported
`sqlite3_open_v2`, `sqlite3_prepare_v2` and `sqlite3_step` addresses to
Mozilla's [SQLite amalgamation](https://github.com/mozilla-firefox/firefox/blob/a34c4160e3f75ab9918fbe4669ff7ae56f1977c8/third_party/sqlite3/src/sqlite3.c),
whose source disclaims copyright. These two Windows Firefox distributions
therefore add IJG and public-domain SQLite conflicts under the issue's
strict OSI-only rule; this is not a claim that either is generally unlawful.
The gate rejects these exact library hashes independently of an audit record.

## Required review record and remaining gaps

The gate also fails unless `licenses/binary-audit.json` has `schemaVersion: 3`
and a `targets` array with exactly one matching, completed review per target.
Each target records `platform`, `arch`, `electronVersion`, `nodeVersion`,
`nodeExecutableSha256`, `chromiumNoticesSha256`,
`electronDistributionSha256`, `packageLockSha256`,
`firefoxExecutableSha256`, `firefoxCoreSha256`,
`firefoxDistributionSha256` and a nonempty `evidence` reference. Schema 2
records are no longer accepted. The check reports the expected values when
no record matches. Distribution digests cover names, file contents,
directories and internal symlink targets; external symlinks are rejected.
Firefox's digest covers its runtime directory or, on macOS, the entire app
bundle. The smoke test fingerprints the selected native executable and
distribution before and after the test and writes
`reports/firefox-runtime.json` with report schema 2; the Linux SQLite library
has a separate identity in that report. The gate rejects missing, older or
mismatched smoke evidence. A changed Node executable, lockfile, Electron
distribution or Firefox runtime invalidates the corresponding review.

The record's evidence must actually cover all bundled components, external
build/test tools and distribution obligations. The automated identities do
not yet enumerate or fingerprint every such tool, including packaging tools,
manual browser-test harnesses and OS dependencies; a matching record alone
cannot establish a complete audit. No complete toolchain inventory, binary
SBOM or review record currently exists.

The Windows Electron 45.2.1 notice file contains 500 component entries. The
supported Electron 43.8.7 and 44.10.2 Windows x64 binaries were also inspected:
both contain the same Ooura FFT notice, so merely switching to either supported
release line does not remove this blocker. These checks are not complete
reviews of those releases. Electron 45.2.1's Linux x64 and macOS x64/arm64
archives also contain that notice; inspecting archives is not evidence that
the application was built or run on those platforms.

`npm run sbom` emits the npm dependency graph as CycloneDX. CI is configured
to retain the lockfile, npm SBOM, npm license report and Electron's bundled
`LICENSE*` files as artifacts. The SBOM does not yet inventory every bundled
binary or OS-level dependency. Complete the cross-platform binary audit and
required distribution notices before publishing.
